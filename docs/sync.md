# Home-directory sync

`sh sync` selects `dotfiles/base` and the matching OS layer, discovers both with `tools/sync/links.py`, and reconciles the combined desired symlinks under `$HOME`. Each relative destination has one owner; duplicate and overlapping claims are rejected before any mutation.

Run `sh sync plan` to preview the dependency graph, link repairs, and local installation state. Resolve each `CONFLICT` before syncing. `sh sync links` applies only the layer links, without tool installs or host setup, and `sh sync tools ish` installs or updates the named tool only. `sh sync` orders links, host prerequisites, tools, and Claude/Pi MCP registration by explicit dependencies. A failed task blocks downstream tasks without undoing independent completed work. `TARGET` changes the symlink destination; `apply`, `tools`, `bridge`, and `uninstall` refuse a target different from `HOME`.

`sh sync tools img` installs the newest `release-<sha>` prerelease of `img` from the public `joshuarli/img` repository, verifying the ZIP against `SHA256SUMS` before replacing the binary. Supported assets are macOS ARM64 and static Linux x86-64/ARM64. Download or checksum failures preserve the installed binary. `img` joins the default tool set on those hosts; each release includes a corresponding-source archive.

`sh sync doctor` inspects task postconditions and retains the platform-specific environment diagnostics without changing managed files or host settings. It reuses `sync plan` to report missing, conflicting, or obsolete layer links, checks ownership records and default `sync tools` launchers (`sh sync list`), verifies shared agent entry points, and checks Homebrew bundle state on macOS or the installed Unbound configuration on Alpine. It may create temporary scratch files, which it removes. It performs no installation, package upgrade or sudo operation; on machines where `agy` is installed it makes one read-only `agy models` request to determine Antigravity login state, and every other login probe is local; a nonzero exit means at least one problem was detected. Use `sh sync plan` to see exact link repairs before applying anything.

`sh sync plan`, `doctor`, `links`, `tools` and `apply` print one row per task that needs attention (`apply`, `conflict`, `failed`, `blocked`, plus `tolerated` and `login` when they occur), with link changes indented under `links`, and end with a one-line summary such as `✓ 7 applied · 39 up to date` or `✗ 1 conflict · 2 to apply · 39 up to date`. Successful `applied`, `current` and `check` tasks are left out by default; add `--show-all` to list every task, or `--json` for one machine-readable object (`schema: 1`, `command`, `host`, `tasks[]` with `name`/`state`/`detail`, `counts`). The installer prints no per-tool install lines by default; set `SYNC_VERBOSE=1` to show them. Color is used only on a terminal and honours `NO_COLOR`.

`plan`, `doctor` and `apply` also probe every sync-installable harness that is present under `~/.local/bin` — `codex`, `claude`, `devin`, `opencode`, `pi`, `cmd`, plus the optional `muse`, `agy` and `fx` — and print one `auth:<harness>` row per harness that is not signed in, for example `auth:devin  not signed in — devin auth login`. The probes run in parallel, are read-only, never print account data or credential material, skip absent binaries, and never change the exit status. Detection is local where the harness provides a local status signal (credential files for Devin, Command Code, Pi and Muse, `codex login status`, `claude auth status`, `opencode auth list`, `fx status --json`); `agy` uses its own read-only `agy models` check because Antigravity exposes no offline probe. DeepSeek Harness is disabled, so its launcher is not probed. Pi is only consumed through `pi-subagent-bridge`, and the `pi-auth` task keeps its credential seeded from the OpenCode login on hosts that have applied sync (the key resolves at runtime), so Pi stays quiet there; `sh sync plan` flags it otherwise. Signed-in harnesses stay quiet. `counts` in `--json` gains a `login` key, and `sync hosts` shows the rows without treating hosts as unhealthy.

## Every host

`sh sync hosts [pull|plan|doctor|apply] [HOST...] [--all] [--show-all]` runs on the machines in the `hosts` map of [`tailscale/policy.json`](../tailscale/policy.json), in parallel. `HOST...` selects machines; omitting it, or passing `--all`, selects every policy host. `--show-all` lists up-to-date tasks in the results. `sh sync apply --all`, `sh sync plan --all` and `sh sync doctor --all` are shorthand for the corresponding `hosts` command; a fleet run has no `--json` output. Add a machine there with its MagicDNS name and tailnet IP. The machine whose IP is local runs in the invoking checkout; the others use SSH and their own `~/usr`. The output lists each host, revision, checkout state and sync summary, followed by tasks needing attention. `*` marks this machine. Each host prints one progress line to stderr as it finishes, so a slow host is visible before the table prints; the table itself still waits for every host. A host whose sync step fails is reported without discarding the other hosts' rows, and network stalls are bounded by a 30-second HTTP timeout instead of hanging the run.

`pull` fetches and fast-forwards `main`. An ahead, diverged or non-`main` checkout is reported without switching branches or rewriting history. `plan` (the default) and `doctor` fetch, then inspect the current checkout. `apply` attempts the pull and skips sync whenever the checkout cannot be verified as updated — a failed fetch, an empty or failed repository check, a diverged or non-`main` checkout, or `pull=blocked` — and fails that host before any sync runs.

Fleet preserves a host doctor's exit status: a nonzero exit fails that host even when its JSON parses, and doctor treats a required probe still in `apply` state as unhealthy. The legacy doctor's diagnostics are printed on stderr for `--json` consumers, so fleet can show the reason instead of certifying the host.

`sh sync uninstall` uses ownership records under `${XDG_STATE_HOME:-$HOME/.local/state}/sync` for layer links and ordinary tool paths. Companion trees use their own receipts. Uninstall aborts before removal when an existing recorded path fails its ownership proof or a companion receipt has drifted. The private installer is `tools/sync/installer.py`; call it through `sh sync` or `sh sync tools NAME`.

`cf` is installed by default from the latest npm package under the managed Node.js runtime. `pnpm` is installed from the newest standalone release binary for macOS arm64/x86_64 and Linux arm64/x86_64 (musl); GitHub's SHA-256 verifies the archive, the staged binary's `--version` is checked before switching, and no npm or Node.js runtime is needed. Its versioned tree lives under `${XDG_DATA_HOME:-$HOME/.local/share}/pnpm-native/releases/` with `bin/pnpm` linked from `~/.local/bin`; the legacy npm prefix at `pnpm-npm` is removed only after a verified switch. `agent-browser` is installed by default at v0.43.0 or newer from `vercel-labs/agent-browser` for macOS arm64/x86_64 and Linux x86_64/arm64 (musl builds), without a Node.js runtime. `sh sync tools agent-browser` installs the latest release: GitHub's SHA-256 verifies its native binary, and npm's SHA-512 integrity verifies the matching **skill-data only** (no npm install, scripts, or JS runtime). The versioned bundle lives under `${XDG_DATA_HOME:-$HOME/.local/share}/agent-browser-native/releases/`, with `current/bin/agent-browser` linked from `~/.local/bin`; `skills get core`, `skills get webmcp-gen`, and `skills get modern-web-guidance` are smoke-tested before switching. The previous binary and its state survive a failed upgrade. Sync removes the legacy npm tree at `${XDG_DATA_HOME:-$HOME/.local/share}/agent-browser` only after a verified switch. The system Chrome/Chromium can be used; `agent-browser install` is optional for managed Chrome for Testing. `stuff` is installed by default from its latest GitHub pre-release; `sh sync tools stuff` updates or reinstalls it.

`sh sync tools uv` installs the latest `uv` and `uvx` from `astral-sh/uv` for macOS arm64/x86_64 and Linux arm64/x86_64 musl, verifies the release `.sha256`, and installs both into `~/.local/bin`. `uv` is in the default target set and the Alpine server profile; the user-local binary takes precedence over a package-manager `uv` in the login PATH.

`sh sync tools vault` installs the newest `release-*` prerelease of `laputa-systems/vault` as `~/.local/bin/vault` for macOS arm64/x86_64 and Linux arm64/x86_64 musl. `vault` is in the default target set on those platforms and in the Alpine server profile; `dsh`, the Claude API launchers, and the tailnet Makefile use it to read secrets.

`sh sync tools devin` installs the Devin CLI from the vendor manifest at `static.devin.ai/cli/current/manifest.json` for macOS arm64 (macOS 27 or later) and Linux arm64/x86_64, verifies the tarball against the manifest `sha256`, and keeps versioned trees under `${XDG_DATA_HOME:-$HOME/.local/share}/devin/cli/_versions/` with `current` and `~/.local/bin/devin` symlinked through it — the same layout as the official installer, which sync adopts rather than duplicates. macOS x86_64 is not a supported platform. `devin` is in the default target set; `devin auth login` remains a separate interactive step, and sync never runs the installer's `devin setup` wizard.

The base layer also links a `yt-dlp` shim. It downloads the upstream nightly on first use and checks for a newer nightly at most once a day; `vdl`, `mdl`, and `mpdl` run through it. Remove `${XDG_DATA_HOME:-$HOME/.local/share}/yt-dlp` and `${XDG_STATE_HOME:-$HOME/.local/state}/yt-dlp` to reclaim the download and its state.

`sh sync` also runs host setup: macOS installs Homebrew packages, while Alpine Linux installs the sync prerequisites and configures Unbound and DNS. These steps can use `sudo`. Other Linux distributions skip Unbound setup. Touch ID, pointing `/bin/sh` at dash (`setup-macos posix-sh`, which `sync doctor` checks), macOS DNS, and Tailscale SSH setup are manual; the packages step installs Homebrew's `tailscale`, the only macOS variant that serves Tailscale SSH. See [`setup-macos`](../host/macos/setup-macos) and [macOS preferences](macos-preferences.md).

On macOS, `sh sync tools ghostty` or `sh sync tools ghostty-custom` installs the latest `release-*` prerelease from `joshuarli/ghostty`. It verifies `SHA256SUMS`, installs `Ghostty Custom.app` with a `~/.local/bin/ghostty-custom` symlink, and records the release asset identity. Set `GHOSTTY_APPLICATIONS_DIR="$HOME/Applications"` if `/Applications` is not writable. It will not overwrite an existing unmanaged app or launcher; `sh sync uninstall` removes a sync-managed installation.

**Ghostty shader reload:** After `git pull`, run `sh sync links` to link any new shader file. Ghostty only rebuilds a shader on config reload when the configured shader path changes; editing GLSL at the same path alone may leave an existing terminal using cached code. Open a new Ghostty window or fully quit and relaunch for source-only changes.

`sh sync tools fx` is an optional native install; the default `sh sync` run does not install fx. The `~/.fx/AGENTS.md` and `~/.fx/settings.json` files are dotfiles-managed links; fx credentials, sessions, and all other mutable state stay local. fx auto-updates are disabled in the tracked profile.

The `host/macos/` directory is not part of the layer sync.

`sh sync tools player` installs the latest tagged Player release from `joshuarli/play` and the exact FFmpeg runtime that release declares. It verifies the release `SHA256SUMS`, reads the declaration (`FFmpeg runtime: <ffmpeg>+release-<commit>` in the Linux tarball's `README`, `PlayerFFmpegRuntime` in the macOS app's `Info.plist`; the older `<ffmpeg>+<YYYYMMDD>` form is still accepted because the published Player v0.43.2 declares it, and installs the matching dated runtime archive), and installs that runtime release through the ffmpeg runtime pin `~/.local/share/ffmpeg/pins/player` without moving the CLI's `current`. The runtime release is the `release-<commit>` prerelease of `laputa-systems/ffmpeg-build` and its archive `ffmpeg-runtime-<ffmpeg>-<triple>.tar.xz` must be for the declared `<ffmpeg>` version. On x86-64 Linux each release is a directory `~/.local/share/player/releases/<tag>-<digest>/` with `bin/player` and a `lib` symlink to the pinned runtime's `lib/` (Player's RUNPATH is `$ORIGIN/../lib`); `~/.local/share/player/current` selects it and `~/.local/bin/player` links through `current/bin/player` (set `PLAYER_HOME` to move the player directory). On macOS it installs `~/Applications/Player.app` (set `PLAYER_APPLICATIONS_DIR` to change the app location) and a `~/.local/bin/player` link; the installer adds the pinned runtime's `lib/` as an absolute `LC_RPATH` to the staged app with `install_name_tool -add_rpath`, signs it ad hoc again, and runs `player --version` before the app replaces the old one, which keeps `~/Applications` free of a sibling `lib` link. The player runs before it is switched in, so a runtime that cannot load keeps the previous player. The old runtime is released only after the new player is selected. Linux still needs Player's own system libraries (Vulkan, Wayland, ALSA, fontconfig, harfbuzz, freetype) and the runtime's `libva`. It refuses an unmanaged existing app or launcher; remove a manually installed copy first. The macOS app is ad-hoc signed and not notarized, so the installer clears the quarantine attribute. `player` is in the default target set on x86-64 Linux and optional on macOS.

`sh sync tools ffmpeg` installs the shared FFmpeg runtime (`ffmpeg`, `ffprobe`, and the seven libav shared libraries) from the newest `release-<commit>` prerelease of `laputa-systems/ffmpeg-build` that lists `ffmpeg-runtime-<ffmpeg>-<triple>.tar.xz` (discovered through `releases.atom`; dated `YYYYMMDD` releases are ignored) for `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, or `aarch64-unknown-linux-musl`. It verifies the release `ffmpeg-runtime-<ffmpeg>-<triple>.manifest.json` and the archive against `SHA256SUMS`, accepts only regular files, directories, and the sibling-name library symlinks directly in `lib/` (absolute, nested, `..`, dangling, cyclic, or non-`lib/` links are refused), and checks `share/ffmpeg-build/manifest.json` (`profile`, `target`, `sources.ffmpeg.version`, `producer.commit` equal to the release commit, and `release.archive`) and every `libraries` entry: the library's SONAME or install name, its `sha256`, and its two version links. On macOS it also runs `codesign --verify --strict` on every program and library. It then runs `ffmpeg -version` and `ffprobe -version` from the staged tree. On Linux the programs need the system `libva` and `libva-drm` (Alpine: `apk add libva`); a runtime that cannot load them fails with that instruction. The tree is installed whole and never modified afterwards under `~/.local/share/ffmpeg/releases/release-<commit>-<triple>-runtime/` (`bin/`, `lib/`, `include/`, `share/`); `~/.local/share/ffmpeg/current` selects the CLI version and `~/.local/bin/ffmpeg` and `~/.local/bin/ffprobe` link through `current`. A corrupted installed tree is replaced from the archive. A failed download, checksum, extraction, validation, signature check, smoke test, or switch keeps the previous installation, and an unmanaged launcher is refused. A tool that links the libraries pins an exact release with `Installer.ensure_ffmpeg_runtime(tool, tag)`: it installs that release if absent without moving `current` (and without network when it is already valid), returns its directory, and records `~/.local/share/ffmpeg/pins/<tool>`. Each sync keeps `current` and every pinned release and removes the rest, including pre-runtime static releases and abandoned staging directories. `tool:player` runs after `tool:ffmpeg`. `ffmpeg` is in the default target set on those three platforms, and `doctor` and the Alpine verifier check both launchers.

`sh sync tools cargo-mutants` installs the newest `release-<sha>` prerelease from the `laputa-systems/cargo-mutants` fork for Linux x86_64/aarch64 (static musl) and macOS x86_64/aarch64, verifies the archive against the release `SHA256SUMS`, and installs `cargo-mutants` in `~/.local/bin` without needing Cargo at install time. `sh sync tools cargo-llvm-cov` installs the pinned `v0.9.2` release tarball from `taiki-e/cargo-llvm-cov` for Linux x86_64/aarch64 (musl) and macOS x86_64/aarch64, verifies the archive against a pinned SHA-256, and extracts `cargo-llvm-cov` into `~/.local/bin` without needing Cargo at install time. Both are default tools on macOS and hosts with `~/.cargo/bin/rustup`, subject to the server profile; running either tool still needs a Rust toolchain, and cargo-llvm-cov needs the rustup `llvm-tools` component.

`sh sync tools zzz` installs the `zzz` CLI from the newest `release-*` release of `laputa-systems/zzz` (discovered through `releases.atom`) as a raw static binary for Linux `x86_64` and `aarch64` musl static; the release publishes no `SHA256SUMS`. `zzz` is in the default target set on Linux and skipped on other platforms. `encode` needs macOS and exits early elsewhere.

`sh sync tools shuck` installs the newest `release-*` prerelease of `joshuarli/shck` (discovered through `releases.atom`) for `aarch64-apple-darwin`, `x86_64-unknown-linux-musl-static`, or `aarch64-unknown-linux-musl-static`, and installs the binary as `~/.local/bin/shellcheck`; shuck runs its ShellCheck compatibility mode under that name. `shuck` is in the default target set on those three platforms and the Alpine server profile.

`sh sync tools lz` installs the newest `release-<sha>` prerelease of `joshuarli/lz` (discovered through `releases.atom`) for `aarch64-apple-darwin`, `x86_64-unknown-linux-musl-static`, or `aarch64-unknown-linux-musl-static`, and installs the binary as `~/.local/bin/less`; lz runs its pager under that name. The macOS build is ad-hoc signed and the Linux build is static-musl. It verifies the archive against `SHA256SUMS` before installing, and `LESS-LICENSE` stays in the release zip. `lz` is in the default target set on those three platforms; the Alpine server profile is unchanged. `~/.local/bin/less` shadows the system pager where it precedes `/usr/bin` in `PATH`.

`sh sync tools bctl` installs the newest `release-*` of `joshuarli/bctl` for `aarch64-apple-darwin` or `x86_64-unknown-linux-musl`. It verifies the archive against `SHA256SUMS-<triple>`, extracts it under `~/.local/share/bctl/releases/<tag>-<triple>/`, and runs the staged `bctl image pull` and `bctl doctor`. Only when both pass does it switch `~/.local/share/bctl/current` and link `~/.local/bin/bctl`, so a failing release leaves the previous one selected. Older releases are pruned. `bctl` is not in the default target set.

`sh sync tools gluon` installs the newest `release-*` prerelease of `laputa-systems/gluon` (discovered through `releases.atom`) for `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, or `aarch64-unknown-linux-musl`. The archive holds the `meson`, `ninja`, and `gluon-build` binaries; the release tree lives under `~/.local/share/gluon/releases/<tag>-<triple>/` (set `GLUON_HOME` to move it) with `~/.local/share/gluon/current` selecting it and `~/.local/bin/meson`, `~/.local/bin/ninja`, and `~/.local/bin/gluon-build` linking through `current`. The archive is verified against `SHA256SUMS`, older gluon releases are pruned, and an unmanaged launcher is refused. `gluon` is in the default target set for `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, and `aarch64-unknown-linux-musl`.

`sh sync tools git` installs Git from the newest `release-<sha>` prerelease of `laputa-systems/git-build` (discovered through `releases.atom`, newest by date, skipping releases that predate the shared build-repository format) for `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, or `aarch64-unknown-linux-musl`. It reads the release `SHA256SUMS` to find `git-<version>-<triple>.tar.xz`, checks `git-<version>-<triple>.manifest.json` against the checksum list (product, version, target, and `source_revision` equal to the tag's commit), verifies the archive against `SHA256SUMS`, and extracts it to `${XDG_DATA_HOME:-$HOME/.local/share}/git/releases/<tag>-<triple>/` (set `GIT_HOME` to move it), with `git/current` selecting it and the Git commands linking through `current`.

`sh sync tools ssh` and `sh sync tools oxish` install `ssh-<version>-<triple>.tar.xz` (the six OpenSSH commands at the archive root) and `oxish-<version>-<triple>.tar.xz` (`bin/oxish-server` and `bin/oxish-session`) from the newest `release-<sha>` prerelease of `laputa-systems/ssh-build`, with the same release discovery, manifest and `SHA256SUMS` checks as Git. The trees live under `${XDG_DATA_HOME:-$HOME/.local/share}/ssh/releases/<tag>-<triple>/` and `.../oxish/releases/<tag>-<triple>/` (set `SSH_HOME` or `OXISH_HOME` to move them).

Sync prunes a recorded link whose old layer source is gone, including a link that mirrored a layer symlink to a home path the layers still provide; `sh sync plan` lists these as `PRUNE`. Foreign links, still-present source links, and unrecorded links are preserved, except two legacy adapters with exact old targets: `~/.claude/AGENTS.md -> ../.codex/AGENTS.md`, which made Claude load the shared contract twice, is pruned, and `~/.claude/CLAUDE.md -> ../.codex/AGENTS.md` is retargeted to the declared bootstrap. To retire a managed link, remove its tracked declaration and run `sh sync links`. Test with an isolated `TARGET` scratch home; the old standalone `sym` command has been retired.

`~/.claude/skills -> ../.agents/skills` is declared in `tools/sync/links.py` instead of as a layer file, because Claude Code would otherwise discover the tracked link while working inside this repository and list every skill twice. A layer file at that path is an error.

## Cross-harness Pi SDK subagent bridge

`sh sync bridge` selects only the managed Node.js/Pi runtime and MCP registration tasks. It does **not** install Command Code, Claude Code, OpenCode, Homebrew packages, or any other npm-managed harness as a prerequisite. Node.js itself is downloaded from the checksum-pinned static artifact mirror when absent; its **bundled** npm is not upgraded or queried against the npm registry.


`sh sync tools pi` installs the runtime selected by [`tools/pi/runtime.pin.json`](../tools/pi/runtime.pin.json). The [Pi runtime guide](pi.md#pinned-npm-free-pi-runtime) owns the artifact verification, cache, profiles and rollback contract. **Ordinary Pi setup and startup make no npm, npx, package-registry, `pi install`, or `pi update` request.** The Pi settings have `packages: []`; any nonempty package declaration is a hard error. Updating the closure belongs to the explicit `/pi-update` workflow.

The `pi-extensions` sync task now validates that offline-only policy without mutation. The `pi-subagent-bridge` dependency directory links to the very same installed runtime, instead of running npm to install a second SDK. `sh sync` registers the bridge with Claude and Pi; Codex reads the tracked `[mcp_servers.pi-subagent-bridge]` entry. The `pi-auth` task runs alongside them on non-server profiles (and via `sh sync bridge`): it seeds `~/.pi/agent/auth.json` with the `opencode-go` provider whose key is the runtime command `!opencode auth export opencode | jaq -r '.[] | select(.active) | .value.access'`, so Pi resolves a fresh OpenCode Go access token itself and sync never stores one. Existing entries — including a user-customised `opencode-go` — and other providers are preserved; an unreadable or non-object `auth.json` is a conflict and is never rewritten. OpenCode never registers the bridge: `sh sync` and `sh sync uninstall` remove an owned OpenCode registration instead, and `sync doctor` verifies it is absent (see the `orchestrate` skill). Foreign MCP servers, credentials and sessions are preserved. Intercom is loaded into **interactive Pi** and uses the included local broker launcher (compiled JavaScript under `headless-usr`), with automatic model wakeups disabled. The intercom companions for the other harnesses are installed by the `companions-mcp` task: Claude gets the `claude-intercom` MCP entry in `~/.claude.json`, Codex reads the tracked `[mcp_servers.codex-intercom]` entry, and OpenCode loads its adapter through the tracked plugins-dir wrapper ([`dotfiles/base/.config/opencode/plugins/agent-intercom.js`](../dotfiles/base/.config/opencode/plugins/agent-intercom.js)), which imports the installed companion's v2 plugin; `sh sync` removes any owned OpenCode `plugins` registration written by earlier builds instead of writing one.

Headless server profiles skip normal MCP registration but can invoke `sh sync bridge` explicitly. Command Code's `cmd login` remains a separate interactive authentication step.

**Boundary:** other sync-managed tools such as Command Code, Cloudflare utilities and npm itself may still use npm and the network. The no-npm contract applies to Pi CLI/SDK/bridge/intercom only, not the entire tool graph.

The former top-level tool installer has moved to `tools/sync/installer.py` and is private. Use `sh sync` for the full setup, `sh sync tools NAME` for an individual tool, and `sh sync list` to see default tools. Historical installation records under `~/.local/state/dl` are retained to recognize existing installs, not as a separate command.

## Python DAG executor

The public `sync` is a POSIX shell bootstrap for the Python standard-library executor in `tools/sync/main.py` and `tools/sync/dag.py`. It tries the managed `~/.local/bin/python3`, `python3` on `PATH`, and `/usr/bin/python3`, checking SQLite, SSL, subprocess execution and an import of the executor. An interpreter that cannot import the executor is skipped. For setup commands, macOS bootstraps `jaq` and managed Python when the managed launcher is absent. Alpine x86_64/aarch64 bootstraps Python only when no working interpreter is available. `plan`, `doctor`, and `links` never install Python as a side effect.

On Linux without `/lib/ld-musl-<arch>.so.1`, the python-build release cannot start, so `python3` installs CPython 3.15 with the sync-managed `uv` instead. Sync runs `uv python install 3.15` with `UV_PYTHON_INSTALL_DIR` set to `${XDG_DATA_HOME:-$HOME/.local/share}/uv-python`, accepts only an interpreter that `uv python find --managed-python` reports inside that directory, checks it with the same sqlite3/ssl/subprocess smoke test, and links `~/.local/bin/python3` and `python3.15` to it. The fallback records the launchers, state file, and uv directory for uninstall the same way a python-build install does, and it installs `uv` first when the sync-managed `uv` is absent. macOS and Alpine keep using python-build. Without the musl loader the default tool list also drops `ffmpeg` and `player`, whose Linux builds still link musl.

[`tools/sync/installer.py`](../tools/sync/installer.py) tracks the newest `release-*` prerelease of `laputa-systems/python-build` (discovered through `releases.atom`, newest by date) for `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, or `aarch64-unknown-linux-musl`. It reads the release `SHA256SUMS`, verifies the `cpython-<version>-<triple>.tar.xz` manifest against it (product, version, target, and `source_revision` equal to the tag's commit), verifies the archive against `SHA256SUMS`, extracts under `~/.local/share/python-build/<tag>/`, rejects unsafe paths, and checks the staged interpreter (sqlite3/ssl/subprocess smoke) before switching the launcher. The bootstrap applies the same discovery; `sync tools python3` and the bootstrap install the same bytes from the same release. Failed downloads or a failing staged check preserve the previous installation. The Alpine bootstrap needs no `jaq`, `libgcc`, or package-manager Python.

Each task declares prerequisites, an observation of current state, an apply operation, a postcondition, and resource ownership. The scheduler topologically orders tasks, detects cycles and missing dependencies, runs disjoint tasks when safe, and prevents downstream tasks from executing after a failed dependency. `sync plan` and `sync doctor` run the task probes without mutating the managed home. Tool tasks retain update-check semantics: a present launcher is not treated as proof that a newer upstream version doesn't exist, so the underlying installer reconciles it on apply. `CHECK` in a plan means an update check will be performed, not that one is known to be necessary.

The private `tools/sync/installer.py` remains a **leaf adapter** for platform-specific downloads, checksum checks, and legacy ownership records. Python invokes it with one tool per task and runs disjoint tasks in parallel up to `SYNC_JOBS` (default: the number of CPUs), starting tasks on the critical path (Node.js, `jaq`, `uv`) first so their dependents are not starved. Each tool owns a disjoint install prefix, launcher, and state file, and the DAG declares every shared prerequisite: Node.js before the npm tools, `pnpm` before `dsh`, and links before tools. `pnpm` is a standalone release binary with no Node.js prerequisite, so it no longer declares one; `dsh` is currently disabled and skips installation rather than invoking npm. Tool output from parallel installs may interleave. The `sync uninstall` compatibility adapter reads existing ownership records and unregisters managed bridge entries from Claude, Pi, and OpenCode, and removes the intercom companion registrations, shims and install trees. `tools/sync/bootstrap.sh` installs just `jaq` and managed `python3` on machines where no Python interpreter exists yet.

Examples: `sh sync tools cmd` resolves Node.js first; `sh sync tools python3` installs the newest verified python-build release directly; `sh sync bridge` selects Node.js, Pi, and bridge registration, without installing Command Code or OpenCode. Set `SYNC_JOBS` to bound concurrency (default: the number of CPUs). A stale `nodejs/current` symlink whose target resolves inside its install directory but is relative or points at an unmanaged release is warned about and replaced with a managed install; a `current` link pointing outside still fails. A previous managed Node release remains selected until its replacement validates. Failed downloads or validation preserve node/npm/npx and allow retry.

### Safe uninstall provenance

The leaf installer declares changed objects before sync fingerprints them. `sync uninstall` preflights recorded files and directories against those fingerprints before removing registrations. Unknown legacy path-only records and modified recorded objects cause refusal. Reinstalling or upgrading through sync can establish fresh provenance.

Companion trees are recorded in their own `.usr-companion.json` receipts, not in the ownership manifest. Removal and replacement validate the receipt's shape and companion identity, compare its recorded inventory with the live tree independently of the desired pin, and preflight every companion root before changing registrations or deleting anything; the check is repeated at the destructive step. A root with a missing, invalid or mismatched receipt — or a modified installation — is refused and preserved, including across a pin bump. `sync uninstall` runs the same preflight before any bridge registration is removed.

### MCP host-independent registration

`sync` does not register the bridge with OpenCode. Instead it removes an owned `pi-subagent-bridge` entry from the OpenCode configuration via `tools/sync/opencode-worker.py` (run by both `sh sync` and `sh sync uninstall`) and drops the ownership record; when the removal deletes an entry and sync runs inside an OpenCode session, the service restart is skipped because it would kill that session, and it prints the manual command instead. The tracked `[mcp_servers.pi-subagent-bridge]` Codex entry invokes the `pi-subagent-bridge` CLI shim by name, so it contains no home or checkout paths and stays identical on every host; checkout moves and other-OS prefixes leave it unchanged. A stale or foreign registration with the same name is never adopted; entries sync does not own are preserved. Unrelated similarly shaped entries are not touched.

## Link reconciliation implementation

The Python link manager comprises `links.py` (Git-aware discovery with `.sym-dir` directory ownership), `link_plan.py` (typed desired/observed state and an immutable global plan), and `link_apply.py` (no-overwrite filesystem operations and ownership recording). A single plan compares **all** sync layers at once, eliminating the old shell `SYM_PLANNED_PRUNES` handoff. The `links` DAG task re-plans and verifies convergence after applying changes.

Before mutation, the planner checks duplicate or overlapping destinations, foreign content, symlink-parent escapes, and ownership-based pruning. The applier checks live snapshots again, operates with directory file descriptors under the physical target root, and uses exclusive symlink creation. New links are fingerprinted into the ownership manifest; preexisting correct foreign links are never claimed. Recovery is per action, using the journal and destination identity described below; there is no transactional rollback of an entire home. Test with `python3 -I tools/sync/test_links.py` and `python3 -I tools/sync/test_integration.py` in scratch homes only.

### Interrupted link installation recovery

New link and replacement writes stage a uniquely identified symlink in the destination directory, persist a small inode-identified journal in the sync state directory, and create the destination via an exclusive hard link. Ownership records and their fingerprints are durably written before the staged inode and journal are retired. If interrupted after destination creation but before recording ownership, `sync plan` reports `RECOVER`, and `sync links` recovers only the same staged inode; a foreign replacement is never adopted. A crash before journaling may leave an inert temporary stage symlink requiring manual cleanup, but cannot create an untracked destination. Inspect journal or filesystem conflicts rather than deleting arbitrary pending files.

If interruption removes the stage but leaves its journal, recovery accepts only the destination with the exact recorded device, inode and link text. A foreign replacement with identical text is refused. Inspect any identity conflict instead of deleting unknown pending state.

### Ownership writer serialization

Every public `sync links`, `sync tools NAME`, and `sync uninstall` writer acquires a blocking POSIX advisory `flock` on the stable `dl-owned.lock` file before reading ownership records. A sync run holds the lease for its whole lifetime, so a second sync process still waits for the first to finish; threads inside one run share the single flock, so parallel tool tasks do not block each other. Leaf installers no longer append to the shared records file while running: each returns its ownership claims in memory, and Python merges those claims (and any superseded-record removals, such as a previous Node.js release) under the lease before fingerprinting them. The lease is deliberately never unlinked: deleting it while another process holds an open descriptor could split the lock into independent inodes. Plans and doctor remain read-only. Invoke the installer through the public `sync` entrypoint; bypassing it bypasses its ownership lease.

### Kache ownership

A freshly installed kache binary under `CARGO_HOME/bin/kache` is now recorded as a managed `K` object with a content fingerprint. A pre-existing foreign kache is left in place and never adopted or uninstalled. The installer and ownership claim run under the shared sync writer lease; uninstall validates the live kache fingerprint before invoking the dedicated `setup-kache uninstall --purge` cleanup. An old path-only kache record remains untrusted until sync actually performs a verified install. The kache task is current only when `CARGO_HOME/bin/.kache-release` names a `release-<sha>` and lists sha256 digests that match the installed `kache` and `kache-engine`; otherwise sync reruns `setup-kache` for a kache it installed. A kache sync did not install is reported as unmanaged and left alone.
