# Home-directory sync

`sh sync` selects `dotfiles/base` and the matching OS layer, discovers both with `tools/sync/links.py`, and reconciles the combined desired symlinks under `$HOME`. Each relative destination has one owner; duplicate and overlapping claims are rejected before any mutation.

Run `sh sync plan` to preview the dependency graph, link repairs, and local installation state. Resolve each `CONFLICT` before syncing. `sh sync links` applies only the layer links, without tool installs or host setup, and `sh sync tools ish` installs or updates the named tool only. `sh sync` orders links, host prerequisites, tools, and the Claude MCP by explicit dependencies. A failed task blocks downstream tasks without undoing independent completed work. `TARGET` changes the symlink destination, but tools still install under `$HOME/.local/bin`.

`sh sync doctor` inspects task postconditions and retains the platform-specific environment diagnostics without changing managed files or host settings. It reuses `sync plan` to report missing, conflicting, or obsolete layer links, checks ownership records and default `sync tools` launchers (`sh sync list`), verifies shared agent entry points, and checks Homebrew bundle state on macOS or the installed Unbound configuration on Alpine. It may create temporary scratch files, which it removes. It performs no installation, package upgrade, sudo operation, or intentional network request; a nonzero exit means at least one problem was detected. Use `sh sync plan` to see exact link repairs before applying anything.

`sh sync uninstall` removes recorded layer links and installed tool paths. It leaves unrecorded pre-existing links and native launchers in place. Ownership records live under `${XDG_STATE_HOME:-$HOME/.local/state}/sync`. The private installer implementation is `tools/sync/install.sh`; call it through `sh sync` or `sh sync tools NAME`.

`cf` is installed by default from a pinned npm package under the managed Node.js runtime. `agent-browser` is installed the same way into `${XDG_DATA_HOME:-$HOME/.local/share}/agent-browser`; change `AGENT_BROWSER_VERSION` in `tools/sync/install.sh` to upgrade. It drives the system Chrome/Chromium, so no browser download is needed; run `agent-browser install` only if you want a managed Chrome for Testing instead. `stuff` is installed by default from its latest GitHub pre-release; `sh sync tools stuff` updates or reinstalls it.

`sh sync tools uv` installs the latest `uv` and `uvx` from `astral-sh/uv` for macOS arm64/x86_64 and Linux arm64/x86_64 musl, verifies the release `.sha256`, and installs both into `~/.local/bin`. `uv` is in the default target set and the Alpine server profile; the user-local binary takes precedence over a package-manager `uv` in the login PATH.

The base layer also links a `yt-dlp` shim. It downloads the upstream nightly on first use and checks for a newer nightly at most once a day; `vdl`, `mdl`, and `mpdl` run through it. Remove `${XDG_DATA_HOME:-$HOME/.local/share}/yt-dlp` and `${XDG_STATE_HOME:-$HOME/.local/state}/yt-dlp` to reclaim the download and its state.

`sh sync` also runs host setup: macOS installs Homebrew packages, while Alpine Linux installs the sync prerequisites and configures Unbound and DNS. These steps can use `sudo`. Other Linux distributions skip Unbound setup. Touch ID, macOS DNS, and Tailscale SSH setup are manual; the packages step installs Homebrew's `tailscale`, the only macOS variant that serves Tailscale SSH. See [`setup-macos`](../host/macos/setup-macos) and [macOS preferences](macos-preferences.md).

On macOS, `sh sync tools ghostty` or `sh sync tools ghostty-custom` installs the latest `release-*` prerelease from `joshuarli/ghostty`. It verifies `SHA256SUMS`, installs `Ghostty Custom.app` with a `~/.local/bin/ghostty-custom` symlink, and records the release asset identity. Set `GHOSTTY_APPLICATIONS_DIR="$HOME/Applications"` if `/Applications` is not writable. It will not overwrite an existing unmanaged app or launcher; `sh sync uninstall` removes a sync-managed installation.

**Ghostty shader reload:** After `git pull`, run `sh sync links` to link any new shader file. Ghostty only rebuilds a shader on config reload when the configured shader path changes; editing GLSL at the same path alone may leave an existing terminal using cached code. Open a new Ghostty window or fully quit and relaunch for source-only changes.

`sh sync tools fx` is an optional pinned native install; the default `sh sync` run does not install fx. The `~/.fx/AGENTS.md` and `~/.fx/settings.json` files are dotfiles-managed links; fx credentials, sessions, and all other mutable state stay local. fx auto-updates are disabled in the tracked profile. Change `FX_VERSION` and its checksums in `tools/sync/install.sh` to upgrade.

The `host/macos/` directory is not part of the layer sync. `agent-learn` and its Codex hook come from the base layer; its LaunchAgent template is installed only when you pass `--schedule` to `agent-learn enable` on macOS. The commands run the agent-memory package in `$AGENT_MEMORY_VENV` (default `~/d/agent-memory/.venv`). When `~/d/agent-memory` is checked out, `sh sync` installs that environment there as an editable install through the managed `uv`, so source edits take effect without reinstalling; `sh sync tools agent-memory` repairs or installs it explicitly, and fails when the checkout is missing. `AGENT_MEMORY_VENV` must be an absolute path. See `~/d/agent-memory/docs/install.md` for the package itself.

`sh sync tools player` installs the latest tagged Player release from `joshuarli/play`. It verifies the release `SHA256SUMS`, installs `~/Applications/Player.app` and a `~/.local/bin/player` link on macOS (set `PLAYER_APPLICATIONS_DIR` to change the app location), and installs `~/.local/bin/player` on x86-64 Linux. It refuses an unmanaged existing app or launcher; remove a manually installed copy first. The macOS app is ad-hoc signed and not notarized, so the installer clears the quarantine attribute. `player` is in the default target set on x86-64 Linux and optional on macOS.

`sh sync tools ffmpeg` installs the `ffmpeg` and `ffprobe` pair from the newest `YYYYMMDD` or `YYYYMMDD-rN` release of `laputa-systems/ffmpeg-build` (discovered through `releases.atom`) for `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, or `aarch64-unknown-linux-musl`. It verifies `SHA256SUMS`, stages the `tools` archive under `~/.local/share/ffmpeg/releases/<tag>-<triple>/`, smoke-tests both commands, then points `~/.local/share/ffmpeg/current` at it and links `~/.local/bin/ffmpeg` and `~/.local/bin/ffprobe` through `current`. A failed download, checksum, extraction, or smoke test keeps the previous pair; an unmanaged launcher is refused. `ffmpeg` is in the default target set on those three platforms, and `doctor` and the Alpine verifier check both launchers.

`sh sync tools zzz` installs the `zzz` CLI from the newest `release-*` release of `laputa-systems/zzz` (discovered through `releases.atom`) as a raw static binary for Linux `x86_64` and `aarch64` musl static; the release publishes no `SHA256SUMS`. `zzz` is in the default target set on Linux and skipped on other platforms. `encode` needs macOS and exits early elsewhere.

`sh sync tools shuck` installs the newest `release-*` prerelease of `joshuarli/shck` (discovered through `releases.atom`) for `aarch64-apple-darwin`, `x86_64-unknown-linux-musl-static`, or `aarch64-unknown-linux-musl-static`, and installs the binary as `~/.local/bin/shellcheck`; shuck runs its ShellCheck compatibility mode under that name. `shuck` is in the default target set on those three platforms and the Alpine server profile.

Sync prunes a recorded link whose old layer source is gone; `sh sync plan` lists these as `PRUNE`. Foreign links, still-present source links, and unrecorded links are preserved. To retire a managed link, remove its tracked declaration and run `sh sync links`. Test with an isolated `TARGET` scratch home; the old standalone `sym` command has been retired.

## Claude orchestration MCP

Desktop `sh sync` installs Command Code alongside the default tools, installs the pinned `@opencode/client` dependency for `tools/opencode-worker`, and registers `usr-opencode-worker` in Claude's user MCP configuration and Pi's `~/.pi/agent/mcp.json`. Codex reads the same server from the tracked `~/.codex/config.toml` (`[mcp_servers.usr-opencode-worker]`). `sh sync plan` previews missing bridge components and `sh sync doctor` verifies them. The operation is idempotent; it preserves other user MCP entries, credentials, and sessions. `sh sync uninstall` unregisters only the owned bridge entries. Headless server profiles skip this step. Sign in separately with `cmd login` if Command Code credentials are missing.

The former top-level tool installer has moved to `tools/sync/install.sh` and is private. Use `sh sync` for the full setup, `sh sync tools NAME` for an individual tool, and `sh sync list` to see default tools. Historical installation records under `~/.local/state/dl` are retained to recognize existing installs, not as a separate command.

## Python DAG executor

The public `sync` is a minimal POSIX shell bootstrap that starts the Python standard-library executor in `tools/sync/main.py` and `tools/sync/dag.py`. On macOS, an absent managed Python is bootstrapped by the existing verified `python-build` installer (with `jaq` as its current bootstrap prerequisite). `plan`, `doctor`, and `links` never install Python as a side effect; they can use an existing Python 3.9+ interpreter. Alpine currently requires an already usable Python; the standalone Alpine bootstrap is explicitly deferred as USR-24 in `TODO.md`.

Each task declares prerequisites, an observation of current state, an apply operation, a postcondition, and resource ownership. The scheduler topologically orders tasks, detects cycles and missing dependencies, runs disjoint tasks when safe, and prevents downstream tasks from executing after a failed dependency. `sync plan` and `sync doctor` run the task probes without mutating the managed home. Tool tasks retain update-check semantics: a present launcher is not treated as proof that a newer upstream version doesn't exist, so the underlying installer reconciles it on apply. `CHECK` in a plan means an update check will be performed, not that one is known to be necessary.

The large private `tools/sync/install.sh` remains a **leaf adapter** for platform-specific downloads, checksum checks, and legacy ownership records. Python invokes it with one tool at a time and serializes those calls under a shared resource lock; the shell script no longer schedules the full tool set. This intentionally preserves hard-earned safety logic while making ordering, filtering, failure handling, and convergence explicit in Python. The `sync uninstall` compatibility adapter reads existing ownership records and unregisters only the managed Claude MCP entry. No YAML DSL, third-party DAG framework, or persistent scheduler state is required.

Examples: `sh sync tools cmd` resolves Node.js first; `sh sync tools python3` resolves `jaq` first; `sh sync bridge` resolves the full Claude/Node.js/Command Code/OpenCode chain. Set `SYNC_JOBS` to bound concurrency (default 4). Legacy installers currently share one write resource, so unrelated tool installations are serialized until their filesystem ownership can be made genuinely disjoint.

### Safe uninstall provenance

Newly installed objects are fingerprinted after the leaf installer confirms an actual change and declares the paths it owns. `sync uninstall` preflights every recorded file and directory against those fingerprints before removing any object, including Claude MCP registration. Unknown legacy path-only records and modified objects cause a fail-closed refusal; sync never silently adopts older objects as owned. Reinstalling/upgrading a tool through sync can establish fresh provenance for it. This deliberately favors protecting user data over removing ambiguous historical installations.

### MCP checkout relocation

`sync` persists a private fingerprint of its own Claude `usr-opencode-worker` registration under the sync state directory. A later checkout move updates this registered path without claiming other MCP servers; stale or foreign registrations with the same name are refused. Existing conventional `~/usr` registrations are accepted for migration, but unrelated similarly shaped entries are not.

## Link reconciliation implementation

The Python link manager comprises `links.py` (Git-aware discovery with `.sym-dir` directory ownership), `link_plan.py` (typed desired/observed state and an immutable global plan), and `link_apply.py` (no-overwrite filesystem operations and ownership recording). A single plan compares **all** sync layers at once, eliminating the old shell `SYM_PLANNED_PRUNES` handoff. The `links` DAG task re-plans and verifies convergence after applying changes.

Before any mutation, the planner checks the complete set for duplicate or overlapping destinations, foreign content, symlink-parent escapes and safe ownership-based pruning. The applier checks the live filesystem snapshots again, operates with directory file descriptors under the physical target root, and uses exclusive symlink creation rather than overwriting a concurrently created foreign file. New links are fingerprinted into the existing sync ownership manifest; preexisting correct foreign links are never claimed. This is per-action crash-safe convergence, **not** a transactional rollback of an entire home. Test it with `python3 -I tools/sync/test_links.py` and `python3 -I tools/sync/test_integration.py` (scratch homes only).

### Interrupted link installation recovery

New link and replacement writes stage a uniquely identified symlink in the destination directory, persist a small inode-identified journal in the sync state directory, and create the destination via an exclusive hard link. Ownership records and their fingerprints are durably written before the staged inode and journal are retired. If interrupted after destination creation but before recording ownership, `sync plan` reports `RECOVER`, and `sync links` recovers only the same staged inode; a foreign replacement is never adopted. A crash before journaling may leave an inert temporary stage symlink requiring manual cleanup, but cannot create an untracked destination. Inspect journal or filesystem conflicts rather than deleting arbitrary pending files.

### Ownership writer serialization

Every public `sync links`, `sync tools NAME`, and `sync uninstall` writer acquires a blocking POSIX advisory `flock` on the stable `dl-owned.lock` file before reading ownership records. It holds the lease until the corresponding filesystem and manifest updates complete, including the legacy tool installer subprocess. The lease is deliberately never unlinked: deleting it while another process holds an open descriptor could split the lock into independent inodes. Plans and doctor remain read-only. Invoke the installer through the public `sync` entrypoint; bypassing it bypasses its ownership lease.

### Kache ownership

A freshly installed kache binary under `CARGO_HOME/bin/kache` is now recorded as a managed `K` object with a content fingerprint. A pre-existing foreign kache is left in place and never adopted or uninstalled. The installer and ownership claim run under the shared sync writer lease; uninstall validates the live kache fingerprint before invoking the dedicated `setup-kache uninstall --purge` cleanup. An old path-only kache record remains untrusted until sync actually performs a verified install.
