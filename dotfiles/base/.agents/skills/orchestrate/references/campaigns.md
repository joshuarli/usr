# Campaigns

A campaign is a backlog too large for one session, run as parallel lanes in rolling tranches: a wave is a selection of ready work, not a barrier, and later tranches start as soon as their prerequisites allow. The parent is the integrator: it selects, briefs, reviews, merges, verifies, and reports to the owner. It writes no feature code while lanes are running.

The lane and closeout steps below require owner-authorized commits. When commits are forbidden, use serial work or disjoint patch handoffs that do not commit. Do not claim commit-dependent closeout or a reboot-safe committed handoff.

### Prepare

- Group the backlog into workstreams by the code they share, so that work likely to conflict is serialized inside one lane. Order the items in each workstream, give each a stable ID, and write prerequisites that cross workstreams on the item.
- State each prerequisite as the narrowest thing the dependent item needs (a store, a type, one call site), and split an item into the part that does not need it and the part that does. The first part starts now and leaves a named seam; the second is a follow-up to the same lane once the prerequisite merges.
- Close product and contract decisions with the owner before assigning. An item with such an open decision is not assigned; a lane that meets one stops on it and reports options. Technical blockers are not owner decisions: the parent resolves them (see Keep every stage busy).
- Before the first wave, measure the tools every lane will run many times and fix what is slow, and make shared architecture changes yourself or in one dedicated lane. Lanes should add to a structure, not invent it in parallel.
- Write the workflow and the lane contract into the repository, and give lanes an agent definition that points at them, so a brief only has to say what is specific to the lane.

### Run a wave

1. **Select.** For each workstream take every ready item whose prerequisites have merged (or whose independent part can start, see Prepare) and that shares its files, as one slice the lane delivers end to end: code, tests, and docs, with what it obsoletes removed. Make the slice as large as one session can finish, so a few big lanes beat many small ones over the same files. Split a workstream across lanes only when its items own disjoint files. A workstream with nothing ready sits out. The wave has one lane per workstream with ready work, plus the lanes for work that does not touch the workstreams at all: docs for what has landed, read-side tooling, experiment plans and measurement harnesses for the close.
2. **Brief.** Item IDs, files the lane owns and files it must not touch, what earlier waves learned, and the report format. The brief is the lane's only context beyond the repository.
3. **Launch** the wave together, each lane in its own worktree under `.work/wt/`, committing on its own branch as Conventional Commits and never pushing. Size the wave by the machine: launch the first lanes, read their peak memory once they build, then set the width from `perf-gate-ready -s` (load and free memory, swap and disk together on macOS and Linux; its `lanes_by_memory` divides free memory by `PERF_GATE_LANE_GIB`, so set that to the measured peak per lane), so the next wave runs as wide as is safe and the machine never swaps or OOMs. Run it before every launch round. Memory, swap and disk are an out-of-memory and swap-thrash precaution for sizing width, not a perf gate: exit 75 means constrained, so add no width and say why. Plain `perf-gate-ready` (no `-s`) still judges timing gates. Do not hold a launch for the previous wave to finish: tranches overlap.
4. **Review, merge, then verify**, one lane at a time as they report. Read the diff, rebase the lane onto the campaign branch, fast-forward, then run the checks for the areas it touched on the merged tree. Run them from a scratch worktree at the merged commit, never in the integration tree, so a slow suite does not block the next merge or change the files under it. After checks pass, follow the [general worktree lifecycle](../SKILL.md#worktree-lifecycle) for that lane. Send a failure back to the lane with the command and its output; send a follow-up in the same files to the lane that holds the context (resume it) rather than starting a new one. Do not hold a merged lane for the slowest one: if its workstream has ready items, brief it again at once on the updated campaign branch.
   Treat the serialized verification queue as a workstream. Track the targets,
   test counts, and unrelated work selected by each focused command. If queue
   wait or verification becomes the campaign's critical path, give loop speed a
   dedicated owner before widening implementation further. Fix selectors,
   expose named tests, split oversized harnesses, or improve revision-safe
   artifact reuse. A broad gate that eventually finishes does not excuse a
   missing focused check; retain the broad gate for the integration risk it
   actually covers.
5. **Close** with every lane merged and none running. Run `codex-campaign-closeout.py begin` from the integration worktree. Run the full checks and performance measurements against the baseline. Run any repository-wide rewrite the wave made possible. Rewrites run here because they change files lanes read. Hold only work that depends on the final state.
   Resolve leftovers using the [general worktree lifecycle](../SKILL.md#worktree-lifecycle). The Codex Stop hook is a campaign closeout guard. It checks registered worktrees before Codex ends its turn, and does not remove them. Keep any retained worktree under `.work/`, commit it, and record its path and reason in the campaign handoff. Then allow it with `codex-campaign-closeout.py allow --path <path> --reason <reason>`.
   If the campaign resumes before closeout passes, run `codex-campaign-closeout.py cancel` before selecting work. Run `begin` again at the next close.
6. **Record.** Delete finished items, add the defects found, and report to the owner: what merged, every contract change, measurements, and the decisions the next wave needs.

### Keep every stage busy

The owner should never have to ask for more lanes or staggered work; the parent does this unprompted, every turn it acts. When the owner does ask, apply the [accelerate](../../accelerate/SKILL.md) skill. These are rules, not tips:

- **A lane that stops is replaced in the same turn.** When a lane reports or stops short of its list, resume it with the ruling that unblocks it, or start a fresh lane on its remainder before doing anything else. A lane whose context is large and slow is replaced by a fresh one, not resumed. Check the ready-work list against the running lanes after every report.
- **Width has a floor and a ceiling.** Keep at least as many lanes running as there is disjoint ready work, up to what the machine allows (set by measured load, swap, memory and disk). Stronger tiers go to the hard remainder; concurrency is not lowered to afford them.
- **Integration overlaps the next wave.** Build and verify the integration branch from finished lanes while the next wave runs. The next wave starts from that unintegrated branch (`git merge --ff-only <integration branch>` as its first step) so it does not redo finished work. Integrate continuously in small groups, not once at the end.
- **Verification runs in parallel on disjoint inputs.** When the serialized check is the critical path, split the candidate set into independent groups and run several at once as memory allows, instead of one long queue. Never run two collects on the same tree.
- **Every wait names its next action.** Schedule a follow-up that states what to do when it fires, with a delay chosen from how long the awaited job takes (no fixed cap), so no stage stalls on the parent. After every report and every wake-up, count the running lanes against the ready work and launch the difference before doing anything else: a wave must never drain while its integration is pending.
- **Parked work is a backlog.** Each round, hand the parked items to a stronger lane with a design task. They are not left in a report.
- **Blockers are the parent's to resolve.** A lane that parks on a technical obstacle (a shared base that needs a design, a contract that needs widening, a checker policy gap, a caller outside the lane's files, a rule the campaign wrote for itself) has found work for the parent, not a question for the owner. The parent turns each recurring blocker into a task the same round: it makes the cross-lane change itself or hands it to a stronger lane with ownership of the extra files, fixes the checker or rule with evidence, and tells the running lanes the new ruling. Escalate to the owner only a decision that changes a product behavior, a public contract, or an authorization boundary, and keep working the rest meanwhile. A list of "decisions only the owner can make" is a smell: re-read it each round and resolve every entry the evidence allows.
- **A rejection of the integration check is routine.** Attribute it to the smallest culprit set, exclude or fix that set, and re-run without stopping the lanes; a policy gap in the checker is fixed in the checker with a test, never by weakening acceptance.

### Lane contract

- A lane owns the design of its slice inside its files: it chooses the structure, writes the tests the slice needs, and settles details itself, logging each call. It stops only on a decision the doc leaves open.
- Lanes never coordinate with each other. A lane that needs something from another workstream reports it; the integrator sequences it.
- Verification belongs to the integrator. A lane uses the cheapest build that compiles its change and runs tests it wrote or changed, by name. It does not run suites, slow or repository-wide checks, or optimized builds. After integration, the parent runs the narrow checks for touched areas, including existing focused regression tests that cover the change. The parent runs broader checks once at the close. A lane's report names what integration should exercise and what it left unverified.
- Shared files are append-only for a lane: add to a registry at the end of its group, put a new unit in its own file, and do not reorganize, rename, or reformat. Registries and lists that every lane appends to (switch overlays, format constants, lock files) take one entry per line, so concurrent lanes merge cleanly; the integrator renumbers format constants at merge.
- A brief may grant a bounded exception to the no-suites rule when the item is judged by a measurement (a batch, a benchmark): the number of attempts, the command, and the scratch output path. Anything not granted stays the integrator's.
- A change in the behavior of existing code is named in the report and ships with whatever makes old code explicit first.
- A lane does not rewrite the corpus, settle an open decision, or fix another workstream's defect. It reports them. It adds a dependency only when the brief names it, because manifests and lockfiles are shared files and the performance-gate measurement is the integrator's check after the merge.
