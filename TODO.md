### USR-81 · P2 · Pi worker runs inherit pi-subagents' 30-minute wall-clock cap

- **Area:** Delegation
- **Where:** tools/pi-subagent-bridge/src/sdk-worker.ts or launch.ts (Pi dispatch), ~/.pi/agent/agents/muse-worker.md (generated by src/policy.ts); pi-subagents src/runs/background/async-execution.js DEFAULT_ASYNC_TIMEOUT_MS
- **Problem:** At installed usr 4e4e7aa871f26776567563cd6713e78be36a5905 the bridge dispatches Pi workers with no timeoutMs or maxRuntimeMs, and the generated muse-worker agent has no defaultTimeoutMs, so pi-subagents applies its DEFAULT_ASYNC_TIMEOUT_MS of 30 * 60 * 1000 as a backstop. Codex and Command Code workers have no such cap. On 2026-11-16 two worker-tier muse-worker runs for Laputa LAP-61 (Asterinas kernel builds and Firecracker guests) ended 'failed' with 'Subagent timed out after 1800000ms.' while still working; run meta b877bdef…_muse-worker_meta.json records timeoutMs null and maxRuntimeMs null. The second run had found and implemented the fix and was verifying it when it was cut off, so its report and ACCEPTANCE line were lost and the parent had to reconstruct the proof. The tier fallback silently changes the run budget from unbounded to 30 minutes.
- **Recommendation:** Set an explicit run deadline for every Pi dispatch from the tier policy (one source of truth shared with the Codex and Command Code lanes), or set defaultTimeoutMs in the generated Pi agent profiles. Surface the effective deadline in worker_start and worker_status, and report a deadline expiry as its own state with the partial output, distinct from a provider failure. Test that a muse-worker dispatch carries the tier's deadline and that an expired run reports it.
- **Fix with:** single-source-of-truth
- **Effort:** S
